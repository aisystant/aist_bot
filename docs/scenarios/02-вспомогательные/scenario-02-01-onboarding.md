# 02.01 Сценарий онбординга

> Slim-онбординг: 5 шагов (имя → длительность → **сложность** → расписание → старт).
> Профиль (occupation/interests/values/goals) — через /profile или /settings после онбординга.
>
> **Обновлено WP-330 С9a (31 мая 2026):** добавлен новый шаг выбора сложности контента (`waiting_for_complexity_level`) между длительностью и расписанием; длительность сокращена до 2 кнопок (10 / 25 мин). Routing 4 версий контента (short_simple / short_complex / long_simple / long_complex) активируется по `(study_duration, complexity_level)` через `core/marathon_content.py:get_day_text(intern=...)`.

---

## Обзор

| Параметр | Значение |
|----------|----------|
| Команда запуска | `/start` |
| Количество шагов | 5 + подтверждение |
| Результат | Готовый профиль Ученика (базовый) + выбор стиля контента |
| Персонализация | Через /profile (отложенная) |

## 1. Определение языка (Шаг 0)

### Автоматическое определение

При `/start` бот определяет язык по `language_code` из Telegram:

| Код Telegram | Язык бота |
|--------------|-----------|
| `ru` | Русский |
| `en` | English |
| `es` | Español |
| `uk`, `be`, `kk` | Русский (близкие языки) |
| `pt` | Español (португальский → испанский) |
| Остальные | English (по умолчанию) |

### Двуязычное приветствие

Если язык неизвестен, бот отправляет приветствие на двух языках (EN + RU).

### Шаг 3: Интересы

| Параметр | Значение |
|----------|----------|
| FSM состояние | `waiting_for_interests` |
| Тип ввода | Текст (через `,` или `;`) |
| Валидация | Парсинг в массив |
| Сохраняется | `interests` (JSON) |

**Сообщение бота:**

**Обработка:**
```python
interests = [i.strip() for i in text.replace(',', ';').split(';') if i.strip()]
# "гольф, чтение" → ["гольф", "чтение"]
```

### Шаг 7: Расписание

| Параметр | Значение |
|----------|----------|
| FSM состояние | `waiting_for_schedule` |
| Тип ввода | Текст (ЧЧ:ММ) |
| Валидация | 0-23 часы, 0-59 минуты |
| Сохраняется | `schedule_time` |

**Сообщение бота:**
```
Во сколько напоминать о новой теме?

_Формат: ЧЧ:ММ (например 09:00). Часовой пояс: Москва (UTC+3)_
```

**Валидация:**
```python
try:
    h, m = map(int, text.strip().split(":"))
    if not (0 <= h <= 23 and 0 <= m <= 59):
        raise ValueError
    normalized = f"{h:02d}:{m:02d}"  # "9:5" → "09:05"
except:
    # Ошибка: "Попробуй ещё раз (ЧЧ:ММ)"
```

- Callback: `confirm`
- Действие: `onboarding_completed = TRUE`
- Переход: финальное приветствие

### Кнопка "🔄" (Редактировать)

- Callback: `restart`
- Действие: возврат к шагу 1
- Данные в БД **не удаляются**, перезаписываются

## 10. OAuth state через PostgreSQL (WP-212)

Онбординг включает OAuth-шаги для интеграций: Aisystant (LMS), Ory (ЦД), GitHub (заметки/публикации), Google Calendar, Linear, Wakatime.

### 10.1. Проблема in-memory state

Раньше OAuth `state` (UUID для защиты от CSRF) хранился в памяти бота. При redeploy Railway — instance перезапускается, memory очищается, callback с редиректа приходит на новый instance → `state` не найден → OAuth падает.

### 10.2. Решение: `oauth_pending_states` таблица

| Поле | Тип | Описание |
|------|-----|----------|
| `state` | TEXT | PK, random UUID |
| `provider` | TEXT | `github` / `ory` / `google_calendar` / `linear` / `wakatime` / `discourse` |
| `telegram_user_id` | BIGINT | ID пользователя |
| `created_at` | TIMESTAMP | Для cleanup (TTL 15 мин рекомендуется) |

См. [tables.md §4.3](../../data/tables.md).

### 10.3. Flow

```
1. cmd_<provider> → generate UUID state
2. oauth_pending_states INSERT (state, provider, telegram_user_id)
3. Отправка redirect URL с ?state=<uuid>
4. User в браузере проходит consent
5. Callback приходит на /oauth/callback/{provider}?state=<uuid>
6. handlers/oauth_callback.py читает oauth_pending_states WHERE state=<uuid>
7. Получает telegram_user_id → сохраняет tokens в *_connections таблицу
8. oauth_pending_states DELETE (или TTL cleanup)
```

### 10.4. Cleanup

Индекс `idx_oauth_states_created` поддерживает cleanup устаревших states. TTL логика — в scheduler (старше 15 минут → DELETE).

### 10.5. Правило

Любой новый OAuth-провайдер должен:
1. Использовать `oauth_pending_states` (НЕ in-memory dict)
2. Указать свой `provider` literal в INSERT
3. Обработать callback в `handlers/oauth_callback.py`
4. Сохранить токены в свою `*_connections` таблицу

## 12. Реферальное приглашение (WP-266 Ф6)

Действующий подписчик вызывает `/invite` (старый алиас `/referral` сохранён) и получает
одну постоянную ссылку без ограничения числа отправок. `/invite` ведёт к статистике
`/invites`, а `/invites` — обратно к созданию приглашений через `/invite`.

Переход `?start=invite_<code>` работает в двух вариантах:

1. Для уже связанной учётной записи бот сразу фиксирует приглашение.
2. Для нового пользователя бот временно сохраняет код в `current_context`, проводит
   обычную регистрацию и фиксирует атрибуцию после появления Ory account.

Активация не создаёт контракт, не выдаёт T2 и не ограничивает бесплатный доступ по времени.
Тексты руководств останутся доступны навсегда; существующие функции с ИИ-генерацией
остаются закрыты подпиской «Инженерия интеллекта». После первой успешной оплаты
приглашённого приглашающему начисляются 3000 бонусов.

## 13. Deep-link источника входа (WP-406 Ф16-B3)

`/start src_<value>` — метка канала привлечения: `site | stand | bot | guide-kit`
(дефолт `bot`; `src_guide_kit` нормализуется в `guide-kit`, неизвестное значение → `bot`).
Не прерывает обычный `/start`: значение сохраняется в
`current_context['onboarding']['entry_source']` и попадает полем `source` в payload
событий воронки онбординга (`onboarding_started` / `x2_completed` / `x3_completed` /
`onboarding_completed`). Не заменяет `entry_type`. Подробности — сценарий 02.11 §4.
