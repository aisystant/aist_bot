## 1. Пользователи и аналитика

### 1.1. `/stats` — общая статистика платформы

**Что делает:** Сводка по пользователям, режимам, языкам, интеграциям.

**Источники:** `dev_stats.get_user_stats()`, `get_language_distribution()`, `get_complexity_distribution()`, `get_integration_stats()`.

**Формат вывода:** HTML-сообщение с 7 секциями:
1. Пользователи (всего, активных сегодня/за неделю/за месяц)
2. Режимы (Марафон / Лента / Оба)
3. Вовлечённость (completion rate, средний streak)
4. Сложность (по Bloom 1-3)
5. Языки (ru/en/es/fr распределение)
6. Интеграции (GitHub / DT / Ory connected)
7. Онбординг (завершён / не завершён)

**Использовать когда:** утренний общий чек платформы, «сколько людей сейчас в марафоне».

### 1.2. `/usage` — популярность сервисов и расписание

**Источники:** `get_global_service_usage()`, `get_schedule_distribution()`.

**Формат вывода:** HTML:
- Топ сервисов с нажатиями и уникальными пользователями
- Расписание: распределение user'ов по часам `schedule_time`

**Использовать когда:** понять, какие сервисы популярны, не перегружен ли какой-то часовой слот (для scheduler load balancing, см. CLAUDE.md §10.16).

### 1.3. `/qa` — статистика консультаций

**Источники:** `get_qa_stats()`, `get_qa_top_topics(8)` (таблица `qa_history`).

**Формат вывода:** HTML:
- Объём: всего / сегодня / неделя
- Качество: 👍 / 👎 процент (`helpful` field)
- Топ-8 тем консультаций

**Использовать когда:** понять, какие вопросы задают, насколько бот полезен на L3.

### 1.4. `/analytics` — сводный аналитический отчёт

**Источники:** `get_analytics_report(hours=24)`.

**Формат вывода:** HTML с 8 секциями:
1. DAU / WAU / MAU
2. Sessions (длительность, команды)
3. Latency p50 / p95 / p99
4. Ошибки (по категориям)
5. Топ команд по нажатиям
6. Самые медленные операции
7. Retention cohorts
8. Тренды с arrow-индикаторами (↑↓)

**Использовать когда:** еженедельный обзор платформы, отчёт в WP-5.

## 2. Наблюдаемость

### 2.1. `/health` — техническое состояние

**Источники:** `get_table_sizes()`, `get_pending_content_count()`, `get_report_stats()`, живой `_scheduler` объект.

**Формат вывода:** HTML:
- **Таблицы:** размеры (строки × bytes)
- **Ожидающий контент:** `marathon_content WHERE status='pending'` — сколько предгенерировано, но не открыто
- **Обратная связь:** новые bug-reports (critical / high / medium / low)
- **Процессы (scheduler):** список cron jobs с расписанием

**Использовать когда:** быстрый health-check после деплоя.

### 2.2. `/latency` — отчёт по latency

**Источники:** `get_latency_report(hours=24)`, `classify_command()`, `get_color()`, `THRESHOLDS`.

**Формат вывода:** HTML с цветовыми зонами:
- 24h сводка
- Пороги (зелёная / жёлтая / красная зона)
- Запросы по командам с avg / p95
- Медленные spans
- Красная зона (требует внимания)

**Использовать когда:** расследование замедлений, подготовка к WP-211 стилистической оптимизации.

**Связанное:** [P-06 Observability § Performance](processes/process-06-observability.md).

### 2.3. `/errors` — отчёт по ошибкам за 24ч

**Источники:** `get_error_report(hours=24)` (таблица `error_logs`).

**Формат вывода:** HTML:
- Сводка (уникальных / всего / критических)
- Ошибки сгруппированы по `logger_name`
- Последние 8 с emoji-уровнем (L1-L4)

**Важно:** `/errors` **также** показывает `gateway_mcp._rate_limited_total` (WP-209 Ф4) — счётчик Cloudflare 429 events. См. [P-10 §6.3](processes/process-10-gateway-mcp.md).

**Использовать когда:** утренний чек инцидентов, корреляция burst 429 со scheduler ticks.

### 2.4. `/delivery` — отчёт о доставке уроков марафона сегодня

**Источники:** `get_delivery_report()` (таблицы `marathon_content`, `development.user_state`, `notification_log`).

**Формат вывода:** HTML:
- **Сводка:** активные / отправлены / ждут / пропущены
- **Список user'ов** с emoji-статусом и временем:
  - 🟢 прочитано (`delivered_at IS NOT NULL`)
  - 🟡 отправлено, не открыт (`notification_sent_at IS NOT NULL, delivered_at IS NULL`)
  - ⏳ ждёт (`status='pending'`, доставка ещё не наступила)
  - ❌ не доставлено (scheduler пропустил / catch-up не сработал)

**Использовать когда:** утреннее расследование «почему user X не получил урок».

**Связанное:** [P-09 Notification Idempotency](processes/process-09-notification-idempotency.md) — как различаются `notification_sent_at` и `delivered`.

## 3. Ручные триггеры

### 3.1. `/dt_sync` — ручная синхронизация engagement → digital_twins

**Источник:** `sync_engagement_to_dt()` (из [P-07 DT Sync](processes/process-07-dt-engagement-sync.md)).

**Формат вывода:** HTML с counters:
- Synced
- Skipped (нет `user_uuid`)
- Errors
- Первая ошибка (до 500 символов) если есть

**Использовать когда:** после миграции VIEW, после исправления collector-бага, для проверки до ночного cron.

### 3.2. `/tailor` — ручной триггер занятия Портного

> ⚠️ Технически **доступна всем**, но de-facto используется только TD1.

**Источник:** `deliver_tailor_lesson(chat_id, bot, force=True)` — `force=True` обходит idempotency guard.

**Формат вывода:** Текстовое уведомление:
- «Генерирую...»
- ✅ Успех / ❌ ошибка

**Использовать когда:** отладка Tailor delivery flow (WP-149), симуляция занятия «на сейчас».

### 3.3. `/nudge_test` — ручной запуск engagement nudges

**Источник:** `send_engagement_nudges()` (WP-85 Phase 5C).

**Формат вывода:** Текстовое:
- ✅ отправлены + ссылка на логи
- ❌ ошибка с причиной

**Использовать когда:** проверка nudge-логики после изменения правил.

### 3.4. `/ory_test` — тест OAuth flow через Ory

**Источник:** `ory_oauth.get_authorization_url()`, переменная `ORY_CLIENT_ID`.

**Формат вывода:** HTML:
- Client ID
- Generated `state` (UUID)
- Authorization URL
- Inline-кнопка «Войти через Ory»

**Использовать когда:** отладка WP-187 OAuth callback flow, проверка Ory конфигурации.

## 4. Операционные

### 4.1. `/reset` — полный wipe данных пользователя

> ⚠️ **Деструктивная операция.** Требует явного `chat_id` — иначе ошибка.

**Аргументы:** `/reset <chat_id>` (обязателен)

**Источники:** `get_intern(target_id)`, `delete_all_user_data(target_id)` — каскадное удаление по всем таблицам.

**Что удаляется:** профиль (`public.users`), state (`development.user_state`), все ответы, прогресс, подписки, токены (Ory/DT/GitHub), feedback — всё.

**Формат вывода:** HTML:
- Имя пользователя (до удаления)
- Количество удалённых строк
- Детализация по таблицам

**Эффект:** при следующем контакте user пройдёт `/start` как новый → онбординг с нуля.

**Использовать когда:** тестовые аккаунты, запрос удаления персональных данных (GDPR, см. WP-214), очистка demo-user'ов.

### 4.2. `/broadcast_reconnect` — массовая рассылка reconnect после Ory JWT миграции

**Контекст:** WP-209 Ф3 — после смены `access_token: jwt` все существующие user'ы с устаревшим opaque token должны переподключиться.

**Аргументы:** `dry` (preview) или `send` (реальная отправка)

**Источники:** `_get_reconnect_candidates()` фильтрует по:
- `ory_tokens.updated_at` — время последнего refresh
- `dt_connected_at` — время подключения ЦД
- Исключает `bot_blocked = TRUE`

**Формат вывода:** HTML:
- **dry:** первые 20 кандидатов с profile preview
- **send:** итоги рассылки (отправлено / заблокировали / ошибки)

**Использовать когда:** ОДИН РАЗ после миграции Ory auth scheme, потом не нужна.

**Правило безопасности:** всегда запускать сначала `/broadcast_reconnect dry`, убедиться в списке, потом `send`.
