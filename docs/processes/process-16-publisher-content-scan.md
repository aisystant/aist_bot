# P-16 Publisher: content scan + backfill

> R21 Публикатор сканирует индекс знаний в GitHub, находит посты `status: ready` + `target: club` и ставит их в очередь публикации на Discourse. Ежедневный скан ограничен окном давности ради объёма GitHub API — отдельный еженедельный backfill-проход подбирает всё, что выпало из этого окна.

---

## Обзор

| Параметр | Значение |
|----------|----------|
| Тип | Процесс (фоновая доставка контента в клуб) |
| Файл | `core/scheduler.py` (функция `_smart_publisher_scan`) |
| Триггеры | cron `05:07 MSK` (daily, `notify=True`) · `date` +2 мин после старта (`notify=False`) · cron `вс 06:17 MSK` (backfill, `notify=False`) |
| Константы | `PUBLISHER_DAYS=mon,thu`, `PUBLISHER_TIME=10:00`, `PUBLISHER_INTERVAL`, `PUBLISHER_MIN_QUEUE` (env, см. `config/settings.py`) |
| Гейт | `DISABLE_DISCOURSE_PUBLISHER=true` отключает все три job — для инстансов, делящих БД publication/community с прод (см. комментарий в `init_scheduler()`) |

---

## 1. Ежедневный скан (`backfill=False`)

1. Для каждого пользователя с подключённым `knowledge_repo` и Discourse-аккаунтом — сканировать `docs/{текущий_год}/` (месячные папки + подпапки мультиканальных постов).
2. `_is_recent(filename)` — пропускает файлы старше 14 дней (по дате в имени файла), не читая их содержимое. Это оптимизация объёма скана, **не TTL на публикацию**.
3. Из прочитанных файлов — кандидаты: `status == "ready"`, `target == "club"`, не в `published_files/titles`, не в `scheduled_files/titles`.
4. Auto-schedule: в понедельник до 10:00 МСК поставить один свежий пост с тегом `итоги-недели` на этот понедельник; обычные `ready`-посты поставить по одному на свободные четверги в 10:00 МСК. Старые итоги недели автоматически не переносить на следующий понедельник.
5. Queue Watch (`notify=True` only): если запланировано < `PUBLISHER_MIN_QUEUE` — уведомление пользователю с подсказкой по драфтам.

## 2. Backfill (`backfill=True`, еженедельно вс 06:17 MSK)

**Зачем.** Найдено 31.08.2026: пост, который стал `ready` позже, чем через 14 дней после даты в своём имени файла (или просто не попал в первое окно скана), навсегда невидим шагу 2 выше — второго прохода не было. ~40 постов с февраля 2026 простояли в `ready` месяцами без единого шанса на автопубликацию.

**Отличия от ежедневного скана:**
- `_is_recent()` возвращает `True` безусловно — окно давности снято.
- `scan_paths` включает и текущий, и прошлый год (граница года — тот же класс пропуска, что и 14-дневное окно).
- Reconciliation и auto-schedule идентичны ежедневному. Подтверждение о реально добавленных в график постах отправляется всегда; повторный Queue Watch отключён через `notify=False`, потому что его уже выполняет ежедневный скан.

**Компромисс.** Полный ежегодовой скан раз в неделю дороже по GitHub API, чем ежедневный 14-дневный — сознательно принято ради простоты (один код-путь, один параметр) вместо отдельного конфигурируемого окна. Если объём знаниевых репозиториев вырастет настолько, что недельный backfill станет заметен по лимитам API — расширить `_is_recent` до параметра-окна вместо булева флага.

## 3. Concurrency

Все три job (`_smart_publisher_scan`, три регистрации) идут через один `_publisher_scan_lock = asyncio.Lock()` — второй триггер во время ещё идущего скана логирует warning и молча пропускает запуск, не встаёт в очередь. **Lock процессный (in-memory), не межинстансовый** — при нескольких запущенных инстансах бота (или рестарте ровно в момент скана) он не защищает от параллельного запуска между процессами.

Между процессами единственного победителя выбирает DB partial-unique constraint в `schedule_publication()` (`ON CONFLICT (chat_id, source_file) WHERE status IN ('pending','publishing')`). Только INSERT возвращает id; проигравший конфликт получает `None`, считает кандидат уже запланированным и не отправляет повторное подтверждение. Это закрывает конкретную гонку постановки в очередь, но не обещает идемпотентность Telegram при сетевом повторе и не компенсирует падение процесса после INSERT, но до сообщения.

## 4. Факты для журнала событий и Центра уведомлений (WP-568 Ф13)

Публикатор записывает доменные факты о публикациях каждого автора в надёжную очередь `event_outbox`; `_drain_event_outbox` раз в минуту доставляет их в журнал событий платформы (event-gateway → `learning.domain_event`). Код — `core/club_publisher_events.py`.

| Где | Факт | Ключ идемпотентности (`external_id`) |
|-----|------|--------------------------------------|
| постановка в график (скан) | `club_publication.v1`, `status=scheduled`, `scheduled_for` | `club-publication:<instance>:<pub_id>:scheduled:<слот UTC>` |
| `_discourse_scheduled_publish`, успех | `club_publication.v1`, `status=published`, `topic_url` | `club-publication:<instance>:<pub_id>:published` |
| `_discourse_scheduled_publish`, исключение | `club_publication.v1`, `status=failed`, `failure` = `club_unreachable` / `club_rejected` / `unknown` | `club-publication:<instance>:<pub_id>:failed:<минута UTC>` |
| Queue Watch (`notify=True`) | `club_publication_queue_low.v1` | `club-publication-queue-low:<instance>:<account_id>:<дата МСК>` (без учётной записи платформы факт не пишется) |

Telegram-номер из бота не уходит: ключи и данные несут только учётную запись платформы и номер публикации. Если факт не записан (нет учётной записи, сбой записи, журнал выключен), сообщение уходит напрямую, как раньше.

Переключатели окружения (по умолчанию выключены):
- `CLUB_PUBLISHER_EVENTS_INSTANCE` = `pilot` | `prod` — включает запись; значение уходит в поле `bot_instance`.
- `CLUB_PUBLISHER_PILOT_VIA_CENTER` = `true` — пилот (`DEVELOPER_CHAT_ID`) перестаёт получать сообщения публикатора напрямую: их доставляет Центр уведомлений на tsekh-1 (источник `club-publisher` в реестре отправителей). Включать только после проверки опроса на tsekh-1, иначе пилот не получит ничего.

Путь одного сообщения прослеживается по `external_id`: строка `event_outbox` в БД бота → `learning.domain_event` → журнал отправок Центра на tsekh-1. Решение — `DS-my-strategy/inbox/WP-568/DRR-f13-club-publisher-via-center.md`.
