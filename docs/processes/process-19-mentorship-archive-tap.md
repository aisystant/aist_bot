# P-19 Наблюдатель архива переписки наставник↔участник (WP-578 Ф2)

> Архитектурное решение принято пир-сессией Claude+Kimi (17.09.2026,
> `MC-sessions:2026-09/17/2026-09-17-06-wp578-f2-telegram-bridge/`), разбор →
> `DS-my-strategy/inbox/WP-578/DRR-f2-telegram-bridge.md`.

## Зачем

Наставник потока (S1/S2) не может быстро ответить участнику с учётом всей
прошлой истории — переписка разбросана между группой потока и личкой,
контекст держится в голове. Процесс пассивно собирает эту переписку в архив,
чтобы карточка участника (Ф3) и ответ-ассистент (Ф4) могли на неё опираться.

## Границы процесса

**Собирает:** сообщения участников и наставников в зарегистрированных
группах потоков; сообщения участников в их личном чате с ботом.

**НЕ собирает** (честное, задокументированное ограничение — не забытый
случай): человеческую переписку наставника с участником один-на-один в
Telegram — бот технически не видит чужие приватные чаты. Полный охват
возможен только через Telegram Business (подключение к аккаунту наставника,
доступ ко ВСЕМ его личным чатам) — отдельная фаза Ф2б со своим Security
Gate, не реализована.

## Поток данных

```
Сообщение (группа/личка)
  → ArchiveTapMiddleware.__call__  (только enqueue, БЕЗ БД, до RateLimit)
  → asyncio.Queue(maxsize=1000)
  → mentorship_archive_worker()    (фоновая задача, вся работа с БД здесь)
      1. Резолв аккаунта (helpers.dual_write.resolve_ory_id_from_chat)
      2. Резолв потока: группа → app.lookup_stream_chat (chat_id),
         личка → app.lookup_participant_stream (account_id)
      3. Роль автора: stream_reader → mentor/pilot, иначе participant
      4. Согласие: db.queries.consent.get_consent_grant(scope)
      5. Классификация: classify.compute_addressed_to_mentor(...)
      6. Запись: db.queries.mentorship.write_archive_entry (UPSERT по
         telegram_chat_id+telegram_message_id — тот же путь для новых
         сообщений и правок)
  → нет активного потока / нет согласия / ошибка после 3 попыток → молча
    пропущено (событие есть только в логе, не в архиве)
```

## Точка перехвата — почему middleware, а не хендлер

`handlers/channels.py` уже держит catch-all для групповых сообщений (SC.118,
ассистент упоминаний) — первый совпавший хендлер aiogram останавливает
дальнейший роутинг для этого апдейта. Middleware работает НЕЗАВИСИМО от
роутинга хендлеров (оборачивает весь диспетчер), поэтому наблюдатель архива
не конкурирует с SC.118 и не требует правок в нём.

Регистрация в `bot.py`: сразу после `UpdateDedupMiddleware`, **до**
`RateLimitMiddleware` — иначе дроп по частоте сообщений в живой группе терял
бы переписку, которую наставник обязан видеть.

`ArchiveTapMiddleware.__call__`/`ArchiveTapEditMiddleware.__call__` (в общем
`_QueueWriterMixin`) ловят любое исключение из `_maybe_enqueue` — наблюдатель
не имеет права уронить обработку сообщения ни одного пользователя бота, не
только участников WP-578 (найдено холодным ревью 17.09).

## Устойчивость записи

- `write_archive_entry` — UPSERT по `UNIQUE(telegram_chat_id,
  telegram_message_id)`, на конфликте обновляет `text`, `consent_at_write` И
  `addressed_to_mentor` — правка сообщения (например, добавленное упоминание
  наставника) обязана пересчитать признак адресности, не только текст.
- `register_stream_chat` — один повтор при гонке двух одновременных
  `/mentor_stream` на один чат (`UniqueViolationError` на частичном
  уникальном индексе `stream_chat_active_uidx`).
- Reply-to/forward-from цели ищутся через `find_participant_id` (только
  чтение), НЕ создаются автоматически — посторонний, которому наставник
  ответил/переслал чужое сообщение, не заводится как участник потока молча.

## Известные ограничения MVP

- **Личка резолвится только после первого сообщения в группе.** Участник,
  который ни разу не писал в свою группу потока, ещё не имеет строки в
  `participant_core` — его личные сообщения боту до этого момента не
  архивируются. Практически не проблема (участники активны в группе с
  первого дня), но это осознанное, а не забытое ограничение.
- **Наставник отвечает только через reply.** Ответ наставника без reply на
  конкретное сообщение участника не привязывается ни к одному участнику —
  архивируется только строка с reply.
- **Упоминание наставника определяется только по `text_mention`-сущности**
  (Telegram даёт `User.id` напрямую). Простое `@username`-упоминание не
  резолвится в этом проходе — потребовало бы отдельного username→account_id
  сопоставления, не реализовано.
- **Тема форума: создатель темы известен только после рестарта бота, если
  тема встретилась воркеру заново.** Кэш `_topic_creator_is_mentor_cache` —
  in-memory, не переживает redeploy. Деградация мягкая: сообщение всё равно
  архивируется, просто как фоновое (`addressed_to_mentor=false`), пока тема
  не будет замечена снова.
- **Deep-link согласия не реализован и не планируется в этом виде.**
  `/start <payload>` уже занят онбордингом (`handlers/onboarding.py`,
  намеренно не тронут). Вместо ссылки — два способа обнаружения (см. ниже),
  выбранные пилотом 17.09.

## Обнаружение согласия (WP-578, решение пилота 17.09)

`/mentor_consent` требует, чтобы участник сам набрал команду — без сигнала
извне он о ней может не знать. Два способа привести к ней участника
(третий, встроить в онбординг, — не делаем сейчас):

1. **Периодическое сообщение в группе.** `core/scheduler.py:_send_mentorship_disclaimer`
   (задача `'cron', hour=10, minute=13`) раз в `MENTORSHIP_DISCLAIMER_DAYS`
   дней публикует в каждый активный `stream_chat` то же сообщение и ту же
   кнопку, что у `/mentor_consent`. Список активных чатов — новая функция
   `app.list_active_stream_chats()` (SECURITY DEFINER, тот же приём, что
   `app.lookup_stream_chat`; `neon-migrations/sandbox/2026-09-17-wp578-list-active-stream-chats.sql`,
   применение к живой базе — отдельный шаг, не в этом коммите). Дедуп —
   `notification_log` с ключом на основе номера N-дневного периода, без
   отдельной колонки "когда отправлено в последний раз".
2. **`/mentor_invite` — личное приглашение от наставника.** Наставник
   отвечает командой на сообщение участника в группе → бот сам пишет
   участнику в личку тот же запрос согласия. `TelegramForbiddenError`
   (участник ни разу не открывал чат с ботом) — ожидаемый исход, не
   ошибка, наставнику приходит понятное объяснение. Сценарий:
   [`03-микро/scenario-03-37-mentor-invite.md`](../scenarios/03-микро/scenario-03-37-mentor-invite.md).

`CONSENT_PROMPT_TEXT`/`consent_keyboard()` (`handlers/mentorship.py`) — общий
текст и клавиатура для всех трёх поверхностей показа (сама команда, эти
два способа), не три рассинхронизирующиеся копии.

## Тесты

- `tests/test_mentorship_classify.py` — юнит-тесты `compute_addressed_to_mentor`
  (полная таблица истинности правила, включая узкое правило про темы форума).
- `tests/test_mentorship_invite.py` — `/mentor_invite`: нет reply-цели,
  приглашение самого себя, вызывающий не читатель потока, успешная отправка,
  `TelegramForbiddenError` не роняет хендлер и даёт наставнику понятный ответ в личку.
- `tests/test_mentorship_silence.py` — Ф9, страж групповых команд (`/mentor_stream`,
  `/mentor_invite`, `/mentor_note`): посторонний (нет аккаунта, не читатель, модуль
  отключён, сбой базы) не получает ни ответа в группу, ни личного сообщения;
  «не читатель» и «модуль отключён» различимы в журнале; ошибки использования и
  подсказка с настоящими кодами потока уходят наставнику в личку; недоставленная
  личка не роняет команду и оставляет предупреждение. Общие подмены — `tests/mentorship_helpers.py`.
- `tests/test_mentorship_readers.py` — Ф9, контракт `list_reader_streams`: пустой список
  против `RuntimeError` при отключённом модуле, фильтр по своему аккаунту.
- `tests/test_mentorship_note.py` — `/mentor_note` в группе (ошибки использования в личку,
  подтверждение карантина, вызов сервиса заметок).
- `tests/smoke/test_mentorship_middleware.py` — импорт, инициализация,
  `__call__` не падает, команды/чужие типы чатов не попадают в очередь,
  переполнение очереди не ломает основной путь (правило 10.37).
