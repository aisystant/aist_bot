# P-18 Контракт выпуска — pilot → production

## 0. Определения

**Trunk** — единственная основная ветвь разработки (`pilot`), из которой собираются кандидаты планового выпуска. Для каждого выпуска trunk фиксируется конкретным commit SHA; плавающая ссылка на имя ветви доказательством происхождения не является.

**Артефакт** — неизменяемый результат сборки из зафиксированного trunk commit: контейнерный образ, архив или иной развёртываемый пакет. Повторная сборка, даже из того же commit, считается другим артефактом, если её digest отличается.

**Digest** — криптографический идентификатор байтов артефакта, полученный и проверяемый реестром артефактов. Тег, имя версии и commit SHA не заменяют digest.

**Конфигурационный профиль** — версионированное декларативное описание эффективной конфигурации развёртывания: переменных и feature-флагов, ресурсов, адресов зависимостей, миграций, политик доступа и ссылок на версии секретов. Значения секретов в профиль не включаются — только их стабильные идентификаторы и версии. Профиль имеет собственный commit SHA и вычисляемый digest.

**Deployment identity** — тройка: `artifact digest + configuration-profile digest + target environment`. Одинаковый artifact digest с разными профилями — тот же бинарный артефакт, но разные развёртывания; успех одного не доказывает пригодность другого автоматически.

> **Зависимость на Ф3.** Контракт предполагает наличие проверяемого идентификатора результата сборки или деплоя: container digest, Railway build/deployment ID с проверяемой привязкой к результату сборки, либо эквивалентный неизменяемый идентификатор. Создание и подключение такого источника — зависимость на Ф3 («Единый запускатель продвижения»), не требуется как реализация внутри Ф1. У `aist_bot_newarchitecture` сегодня (09.09.2026) такого источника нет: Railway автодеплоит по `git push`, явного проверяемого digest контур не читает и не хранит.
>
> До появления этого источника допускается использовать **git commit SHA как временный суррогат digest**. Manifest обязан явно указать `artifact_identity_kind: git_commit_sha_surrogate`; такое значение нельзя представлять как криптографическую идентичность развёрнутых байтов — суррогат слабее полноценного digest, поскольку не защищает от пересборки одного и того же commit с иным результатом. После появления проверяемого источника в Ф3 использование суррогата прекращается для новых продвижений.

**Pilot** — контролируемая предпроизводственная среда и стадия допуска, в которой кандидат развёртывается на ограниченной аудитории или контролируемом трафике до production. Pilot использует тот же artifact digest, что и последующий production; отличия конфигурационного профиля допустимы только по реестру environment deltas (§2). «Прохождение pilot» означает успешное выполнение обязательных проверок, отсутствие нерешённых блокирующих наблюдений и зафиксированное решение пилота по конкретной deployment identity.

**Пилот** (человек) — назначенный владелец решения о прохождении стадии pilot и о продвижении в production. Только его подтверждение из идентифицируемой учётной записи может разрешить спорную классификацию либо исключение `incident-ok`.

**Release owner** — назначенный пилотом владелец конкретного выпуска: ведёт release manifest (§4), организует классификацию дельт (§5), собирает подтверждения и контролирует сроки обратного переноса (§3, §8). Назначается пилотом на выпуск или на постоянной основе; при отсутствии назначения — выпуск не проходит АрхГейт по стоимости (§8).

**Component owner** — человек, отвечающий за технический разбор дельт в конкретном компоненте/модуле репозитория, привлекаемый release owner'ом как классификатор или co-classifier (§5).

**Плановый выпуск** — выпуск из trunk по опубликованному двухнедельному календарю. Release owner публикует ближайшие даты минимум на четыре недели вперёд. Перенос даты не отменяет обязательства по обратному переносу: если очередной слот отменён, крайним сроком становится более раннее из двух событий — следующий фактически состоявшийся плановый выпуск, или 14 календарных дней после production-хотфикса. Нарушение срока — блокирующая задолженность выпуска.

**Smoke-набор** — версионированный обязательный набор быстрых проверок, определённый CI-конфигурацией репозитория на commit кандидата. Источник истины — CI job и список тестов в том же commit, а не число, записанное в этом контракте.

## 1. Смысл «дрейфа»

Дрейф — это непринесённое расхождение наблюдаемого поведения или установленного инварианта между pilot и production.

Различие SHA, истории коммитов, авторства, времени сборки или формы переноса патча само по себе дрейфом не считается. Разные SHA при одинаковом итоговом дереве либо семантически эквивалентном патче не образуют дрейф.

Для выпуска сравниваются: итоговые деревья и содержимое исполняемого артефакта; эффективная конфигурация с учётом разрешённых различий сред (§2); набор вошедших функциональных и аварийных патчей; наблюдаемые контрактные свойства (маршрутизация, авторизация, биллинг, обработка персональных данных, внешние интеграции, обязательные smoke-сценарии).

Разница признаётся шумом переноса только при зафиксированном доказательстве эквивалентности. Во всех остальных случаях она считается реальной дельтой до завершения классификации (§5).

**Критерий семантической эквивалентности.** Разные SHA не образуют дрейф только при одном из механических доказательств:

1. итоговые Git-деревья проверяемого scope идентичны;
2. для патчей на сопоставимой базе совпадает стабильный `patch-id`, а затронутые конфигурация, миграции, зависимости и сгенерированные файлы также идентичны;
3. эквивалентность получена утверждённой репозиторием нормализацией, правила которой версионированы и воспроизводимы в CI.

Совпадение тестовых результатов само по себе не доказывает эквивалентность. Любой иной вывод («рефакторинг не меняет поведение», «добавлено только логирование») — экспертное, субъективное утверждение. Если хотя бы один участник классификации его оспаривает, эквивалентность может подтвердить только пилот; до подтверждения дельта считается реальной и блокирующей.

## 2. Разрешённые различия сред

Pilot и production легитимно различаются только по заранее объявленным параметрам среды: адреса сервисов/DNS/credentials/секреты; объёмы ресурсов, реплики, тайм-ауты, лимиты; уровни логирования/трассировки/мониторинга; тестовые vs production идентификаторы интеграций; feature-флаги (с владельцем, назначением, допустимыми значениями по средам и сроком пересмотра); параметры безопасного rollout (доля трафика, allowlist, canary/cohort, kill switch); настройки хранения/обработки данных, обусловленные требованиями безопасности или GDPR и документированные.

Различие считается разрешённым, только если присутствует в утверждённом реестре environment deltas. Неучтённая конфигурационная разница — потенциальный дрейф, блокирует обычное продвижение. Разрешённые различия не могут ослаблять обязательные инварианты auth, billing, GDPR, целостности данных или smoke-проверок; добавление такого исключения требует решения пилота.

**Проверка фактической конфигурации (обязательна).** Наличие различия в реестре — необходимое, но не достаточное условие допуска. Snapshot фактической конфигурации по умолчанию получает CI job `capture-runtime-config-snapshot` непосредственно из целевой среды до продвижения; job сравнивает snapshot с ожидаемым профилем и `environment_delta_registry` — обнаруженный дрейф блокирует продвижение.

Если CI job или используемый им источник фактической конфигурации недоступен либо не может достоверно прочитать значение — release owner обязан выполнить проверку вручную. В release manifest фиксируются исполнитель, время проверки, целевая среда, способ и источник получения значений, результат сравнения и причина перехода на ручной режим. До завершения ручной проверки и появления этой записи в manifest продвижение заблокировано. **Недоступность источника не может трактоваться как отсутствие различий.**

Правило прямо закрывает прецедент WP-562 от 05.09: фактический `DISABLE_SCHEDULER=true` при задекларированном `false`, молча отключивший задачи планировщика, должен был быть обнаружен как дрейф живой конфигурации.

## 3. Переходный период (двусторонняя запись)

Текущее состояние признаётся явно: `aist_bot_newarchitecture` легитимно принимает прямые хотфиксы в `new-architecture`, поэтому временно действует двусторонняя запись. Production может содержать аварийный патч, ещё не перенесённый в trunk/pilot — это допустимое переходное состояние, но такая дельта остаётся учтённым долгом, а не превращается автоматически в разрешённое различие сред.

**Целевая модель:** один trunk → один неизменяемый артефакт → pilot → production. В production продвигается тот же артефакт по digest, который прошёл pilot; пересборка «того же исходного кода» отдельно для production не считается продвижением того же артефакта.

**Аварийный путь в переходный период:**

1. Предпочтительно: исправление сначала в trunk, затем ускоренная сборка, smoke, pilot, production.
2. Если тяжесть инцидента не допускает этого пути — разрешён прямой production-хотфикс с `incident-ok` (§7).
3. Для хотфикса обязательно создаётся запись долга переноса: владелец, ссылка на патч, категория риска, срок обратного переноса.
4. Хотфикс переносится в trunk и проверяется через pilot не позднее следующего планового выпуска; иной срок требует отдельного решения пилота.
5. До закрытия долга каждый следующий выпуск обязан показывать этот патч как непринесённый.

**Закрытие переходного периода** — не по дате и не автоматически. Событие закрытия — отдельное письменное решение пилота о включении режима single-writer после одновременного выполнения условий: все известные production-only патчи перенесены в trunk либо явно отклонены пилотом; реестр непринесённых патчей пуст; минимум 30 календарных дней и не менее двух последовательных production-выпусков прошли без прямой записи в production; подтверждено, что один и тот же артефакт по digest последовательно проходит pilot и production; аварийная процедура и audit-trail `incident-ok` проверены хотя бы учебным прогоном.

После закрытия переходного периода прямой production-хотфикс не является штатным механизмом — аварийный выпуск идёт через trunk и ускоренный pilot. Возврат к прямой записи требует отдельного, ограниченного по времени решения пилота с планом восстановления single-writer.

## 4. Release manifest — связь commit, артефакта и профиля

> **Не путать с `Release Drift Manifest` (§5).** Здесь — машинный, CI-генерируемый манифест конкретного кандидата (digest, профили, smoke). В §5 — отдельный человеко-заполняемый журнал классификации дельт pilot↔production. Оба обязательны, оба неизменяемы после принятия, но это два разных документа с разным автором и назначением.

Для каждого кандидата CI создаёт неизменяемый release manifest:

```yaml
release_id:
trunk_commit:
artifact:
  registry_ref:
  digest:
  artifact_identity_kind:   # "digest" | "git_commit_sha_surrogate" (см. §0, зависимость на Ф3)
  build_run:
configuration_profiles:
  pilot:
    repository_commit:
    path:
    digest:
  production:
    repository_commit:
    path:
    digest:
environment_delta_registry:
  repository_commit:
  digest:                   # обязателен, симметрично configuration_profiles
smoke:
  ci_config_commit:
  job:
  timeout_policy:           # см. §6
  executed_test_ids_manifest:   # см. §6
pilot_evidence:
production_evidence:
```

Manifest сохраняется в governance-репозитории и после принятия адресуется своим commit SHA. Сборочный CI подтверждает связь `trunk_commit → artifact digest` и подписывает provenance. Deployment job проверяет artifact digest и profile digest до развёртывания и записывает фактически применённую deployment identity.

`environment_delta_registry` идентифицируется одновременно `repository_commit` и `digest`. Отсутствие любого из этих полей, невозможность проверить digest либо несовпадение digest с содержимым реестра блокирует продвижение.

Один artifact digest может применяться с pilot- и production-профилями, но: (1) оба profile digest заранее указаны в одном release manifest; (2) их различия исчерпывающе покрыты утверждённым реестром environment deltas; (3) фактическая конфигурация каждой среды отдельно сверена с её профилем (§2); (4) production-развёртывание запрещено, если переданный profile digest отличается от указанного в manifest. Ручное изменение конфигурации после проверки создаёт новую deployment identity и аннулирует прежнее доказательство прохождения среды.

## 5. Классификация дельт

**Минимальная компетентность.** Автор классификации до вынесения результата обязан: изучить происхождение обеих сравниваемых версий, связанные PR, incident-записи и мотив исходного изменения; уметь объяснить назначение каждой дельты и последствия её отсутствия в trunk и production; проверить затронутые код, конфигурацию, миграции, зависимости и тесты; приложить воспроизводимые команды, diff и доказательства; иметь опыт ревью/сопровождения затронутого компонента либо привлечь co-classifier с таким опытом. Автор переноса не может быть единственным подтверждающим классификатором. Если причина существования хотя бы одной версии патча не установлена — дельта автоматически считается реальной, а не «шумом переноса».

**Процесс до реализации Ф2 (детектора)** — ручной, по шагам:

1. Автор переноса заполняет строку в `Release Drift Manifest`.
2. Редактор сверяет дерево/patch-id и описывает, почему дельта — шум переноса либо реальное поведенческое расхождение.
3. Один или несколько критиков независимо проверяют классификацию редактора. Каждый участник фиксирует собственное решение и доказательства. Согласие выводится только при отсутствии возражений всех назначенных участников.
4. **Любое разногласие между любыми участниками классификации** — автором, редактором, одним или несколькими критиками — означает отсутствие консенсуса. Дельта считается реальной и блокирующей до решения пилота. Решение большинством голосов не применяется; разногласие двух критиков обрабатывается так же, как разногласие редактора и критика.
5. Для категорий GDPR, billing и auth окончательное принятие реальной непринесённой дельты всегда требует явного подтверждения пилота.

`Release Drift Manifest` — обязательный письменный артефакт конкретного release candidate, хранящийся вместе с записью выпуска/PR продвижения и связанный с digest артефакта. Устное решение, сообщение без устойчивой ссылки или локальный файл исполнителя не считаются фиксацией. После выпуска manifest не редактируется молча — исправления оформляются новой ревизией с автором, временем и причиной.

Минимальные поля: release ID и digest; pilot SHA и production SHA; перечень дельт; классификация `transfer-noise | real-delta | unresolved`; категория риска; доказательство классификации; автор классификации и подтверждающий; решение пилота и его время; связанный incident/ticket; владелец и срок обратного переноса.

## 6. Инварианты выпуска и smoke

Для любого продвижения, включая аварийное: обязательный smoke-набор репозитория должен завершиться успешно; результат smoke связан с точным digest продвигаемого артефакта; известны исходный trunk commit, digest артефакта и конфигурационный профиль; все дельты pilot↔production классифицированы либо явно приняты через действительный `incident-ok`; изменения auth, billing и GDPR не могут быть скрыты в категории «прочее»; rollback или безопасное отключение изменения определены до production-продвижения; после аварийного production-хотфикса повторный smoke обязателен на фактически развёрнутом варианте.

`incident-ok` отменяет только инвариант «нет непринесённого реального дрейфа». Он не отменяет smoke, идентификацию артефакта, учёт дельт, требования безопасности, фиксацию решения или обязанность обратного переноса. Падающий или отсутствующий smoke нельзя легализовать меткой `incident-ok`; исключение из этого правила — отдельное принятие операционного риска пилотом, не обычный выпуск.

**Timeout policy.** `timeout_policy` устанавливается по формуле **×8 от измеренного фактического времени прогона**. Начальное значение — **120 секунд** (факт на 09.09.2026: ~15 сек на 476 тестах). CI автоматически формирует сигнал на пересмотр `timeout_policy`, когда фактическое время любого прогона достигает **50% действующего порога** (для начального порога — 60 секунд). Сам сигнал не изменяет порог автоматически: новое значение рассчитывается по той же формуле на основании зафиксированного измерения и принимается пилотом до следующего изменения контракта или конфигурации. Изменение состава smoke-набора или временного порога — отдельное reviewable-изменение; автоматическое увеличение порога при медленном прогоне запрещено.

**Проверка фактически выполненного состава.** CI обязан выгрузить машиночитаемый список уникальных идентификаторов тестов, фактически выполненных в smoke-прогоне. Список автоматически сверяется с разрешённым списком, зафиксированным CI-конфигурацией для данного профиля и commit — сверка требует точного совпадения множеств: отсутствующий, дополнительный, неизвестный либо дублированный идентификатор блокирует продвижение. Тест со статусом `skipped`, `not run`, `filtered out` или эквивалентным не считается фактически выполненным; если его идентификатор входит в разрешённый состав — сверка завершается ошибкой. Одной декларации job о количестве или успешности тестов недостаточно.

## 7. Эскейп-хэтч `incident-ok`

Обход в виде простого наличия строки/тега `incident-ok` в тексте коммита **не принимается**: он не подтверждает личность владельца решения, объём принятого риска и связь с конкретным артефактом.

`incident-ok` действителен только при audit-trail:

1. Создана неизменяемо адресуемая запись исключения с уникальным ID.
2. Запись связана с release ID, точным digest артефакта и `Release Drift Manifest`.
3. В ней указаны инцидент, срочность, непринесённые патчи, категории риска, ожидаемое влияние, rollback, владелец переноса и срок закрытия.
4. Пилот оставил явное подтверждение с идентифицируемой учётной записи — **именно на commit, содержащий окончательные artifact digest, profile digest, scope и срок действия**. Сообщение в чате, устное разрешение или trailer без такого review разрешением не являются.
5. Гейт проверил наличие этого подтверждения и успешный smoke.
6. В commit/release metadata может присутствовать trailer `Incident-OK: <record-id>`, но он — только ссылка, не разрешение сам по себе.
7. Разрешение одноразовое: действует только для указанного digest и конкретного продвижения. Повторное использование для следующего артефакта запрещено.
8. Закрытие исключения фиксируется после обратного переноса патчей и повторной проверки через pilot.

**Временное хранение до Ф3.** До ввода специализированной системы единственная допустимая запись исключения — YAML-файл в governance-репозитории:

`release-governance/incident-ok/WP-562/<exception-id>.yaml`

```yaml
schema_version: 1
exception_id:
incident_id:
release_id:
artifact_digest:
pilot_profile_digest:
production_profile_digest:
target_environment: production
reason:
accepted_risks:
allowed_scope:
expires_at:
requested_by:
pilot_approved_by:
pilot_approval_reference:
created_at:
supersedes:
```

Запись создаётся отдельным PR. `pilot_approved_by` действителен только при approve/review пилота из идентифицируемой учётной записи именно на commit с окончательными artifact digest, profile digest, scope и сроком действия. Перезапись существующего исключения запрещена: исправление — новый `exception-id`, поле `supersedes` ссылается на старую запись. Release manifest хранит эту неизменяемую ссылку.

Если текущая инфраструктура ещё не умеет технически валидировать подтверждение — в Ф1 применяется ручная проверка редактором и критиком, а пилот подтверждает запись до запуска production-продвижения. Автоматизация этого контроля — последующие фазы, контракт этим не ослабляется.

## 8. Владелец процесса и стоимость

Release owner владеет manifest, организацией классификации, сбором подтверждений и контролем сроков. Component owners отвечают за технический разбор своих дельт. Пилот отвечает за спорные решения и исключения, но не за подготовку доказательств.

Для каждого выпуска release owner до начала классификации составляет бюджет: число дельт; назначенные классификаторы и component owners; оценка трудозатрат по каждой дельте; резерв на повторную проверку и решение разногласий; крайний срок доступности пилота.

**Исчерпание резерва.** Если резерв на повторную проверку и разрешение разногласий исчерпан, а разногласие не устранено — дальнейшее внутреннее обсуждение не продлевает резерв: вопрос немедленно и принудительно эскалируется пилоту, продвижение остаётся заблокированным. Если решение пилота не получено до release deadline — результат выпуска `❌`. Базовый бюджет проверок нельзя использовать как неявное продолжение исчерпанного резерва.

Фактическое время фиксируется после выпуска. Если назначенный владелец отсутствует, бюджет не согласован, накопившиеся дельты не укладываются в окно выпуска либо пилот недоступен до установленного дедлайна — АрхГейт получает ❌ по стоимости/операционной исполнимости, выпуск блокируется. Задержка ожидания считается стоимостью процесса, не внешним обстоятельством.

## АрхГейт ЭМОГССБ

Conjunctive screening — профиль не сворачивается в средний балл. Любая характеристика с `❌` блокирует принятие целевой модели; `⚠️` требует владельца меры и срока.

| Характеристика | Профиль | Оценка |
|---|---:|---|
| Эффективность | ✅ | Один артефакт устраняет повторную сборку; обязательный smoke достаточно быстр (порог §6) для запуска даже при инциденте. |
| Модифицируемость | ✅ | Single-writer и обязательный обратный перенос уменьшают расхождение ветвей; manifest локализует технический долг. |
| Отказоустойчивость | ⚠️ | Аварийный путь предусмотрен, но до закрытия двусторонней записи сохраняются конфликты переносов и риск production-only исправлений. Нужны владелец и срок каждого долга (§3). |
| Гибкость | ✅ | Управляемые feature-флаги, canary и временный аварийный путь без отказа от целевой модели. |
| Совместимость | ⚠️ | Различия конфигураций и внешних интеграций могут маскировать поведенческий дрейф. Требуются реестр environment deltas и проверка контрактных сценариев (§2). |
| Стоимость | ⚠️ | Допустима для Ф1 только при выделенном владельце и измеряемом бюджете (§8); ручной процесс не должен стать постоянным. |
| Безопасность | ⚠️ | Явное подтверждение пилота и отдельные категории GDPR/billing/auth снижают риск; ручная классификация остаётся уязвимой к ошибке. Для чувствительных категорий — обязательный conjunctive veto: неразрешённая дельта блокирует выпуск (§5). |

**Вывод.** Целевая модель принята как направление при сохранении перечисленных обязательных гейтов. Переход из `⚠️` в устойчивый режим зависит от реализации детектора дрейфа (Ф2), технической проверки audit-trail (Ф3) и формального закрытия двусторонней записи (§3). Хранилище для записи `incident-ok` решено (§7, временный YAML-путь до Ф3). Открытыми вопросами вне рамок Ф1 остаются: конкретное хранилище для `Release Drift Manifest` (§5) и полномочия заместителя пилота на время его недоступности — оба требуют отдельного решения пилота.
